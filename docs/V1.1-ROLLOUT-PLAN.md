# Shipping v1.1 without touching production

Written 6 Oct 2026, from a measured read of both working trees, the live
container and the live database. Every claim below was checked, not inferred.

## The short answer

**Yes — and the isolation you want is already in place.** Production is pinned
to `main`; all v1.1 work is on `dev`; `main` is 0 commits ahead of `dev` in both
repos, so there is no divergence to untangle.

But the v1.1 drop is **two different things with very different risk**, and
treating them as one release is what would break something:

| | state | ship? |
|---|---|---|
| **Landing page + auth shell** | works, 35/35 tests, wired | **yes, now** |
| **v1.9 calendar groups** | foundation missing, suite down | **no — cannot run** |

## Group A — landing page and auth shell: ready

Frontend only. No backend dependency, no migration, no new table.

- `pages/LandingPage.tsx` (1,456 lines), `components/AuthShell.tsx`,
  `public/landing/`, plus reworked `Login`, `ForgotPassword`, `Onboarding`,
  `Terms`, `AuthCodePanel`.
- **35/35 frontend tests pass**, including 10 dedicated landing-page tests.

**The one production-visible change to be deliberate about.** `App.tsx` changes
exactly one route:

```
-  path="/"   ->  <PublicLayout><Home /></PublicLayout>
+  <Route path="/" element={<LandingPage />} />
```

That is the whole diff. The public root becomes the new landing page. It is the
intended change, but it is the change your existing visitors will see first, so
it wants a Vercel **preview deploy** looked at before it reaches the production
alias — not a merge straight to `main`.

## Group B — v1.9 calendar groups: blocked, and currently breaking the suite

The handoff describes this as a migration to run "after the three earlier
calendar migrations". **Those three phases are not in this repo, and never
were.** `main` contains no calendar code and no reference to
`calendar_integrations` or `appointments`.

What the ZIP dropped in is **Phase 4 of 4, with Phases 1–3 absent.**

### Missing code the new files require

| required by | missing |
|---|---|
| `lib/calendar-booking.js` | `lib/calendar-tokens.js` |
| `api/routes/index.js` | `api/routes/integrations.js` |
| `api/routes/index.js` | `api/routes/internal-calendar.js` |

### Missing tables in the live database

Checked directly against production Supabase:

```

appointments              DOES NOT EXIST
calendar_tokens           DOES NOT EXIST
business_groups           DOES NOT EXIST
```

`20261006_business_groups.sql` itself only creates `business_groups` and
`business_group_members` and references `organizations`, so it *would* apply
cleanly — but the code that uses it reads `calendar_integrations` and
`appointments`, which do not exist. Applying the migration alone buys nothing
and leaves two empty tables behind.

### Two things are actively broken right now

1. **The server test suite does not run at all.** The ZIP overwrote
   `test/run.js` with a version that requires four test files from the earlier
   phases — `crypto.test`, `integrations-oauth.test`, `calendar-booking.test`,
   `calendar-tool-definitions.test` — none of which exist. `node test/run.js`
   crashes with `MODULE_NOT_FOUND` before running anything. You have gone from
   126 passing tests to no measurement at all. The handoff's "199/199" was true
   of the tree it was built in, and is not reproducible here.

2. **The routes were patched into dead code.** The ZIP's changes landed in
   `api/routes/index.js`. Nothing requires that file — `dev-server.js` loads
   `api/index.js`, which has **zero** mounts for `business-groups`,
   `integrations` or `internal-calendar`. `api/routes/index.js` was already
   unresolvable at `HEAD` (it resolves siblings as `./routes/x` from inside
   `api/routes/`), so it is a stale duplicate of the app entry. Even with every
   missing module supplied, the calendar endpoints would not be mounted.

`pages/Integrations.tsx` (1,018 lines) has the matching problem on the
frontend: it is not routed in `App.tsx`, so it is unreachable, and it carries
the only TypeScript error in the tree —
`Type '"integrations"' is not assignable to type 'SettingsTabKey'`.

## The plan

### 1. Preserve the calendar drop, un-break `dev`

Nothing gets discarded. Move the Phase-4 files onto their own branch so `dev`
goes back to a tree that builds and tests, and the calendar work waits for its
foundation.

Server — keep: `lib/calendar-booking.js`, `lib/calendar-sync.js`,
`api/routes/business-groups.js`, `migrations/20261006_business_groups.sql`,
`test/calendar-groups.test.js`.
Restore to `HEAD`: `test/run.js`, `api/routes/index.js`.

Frontend — keep `pages/Integrations.tsx` on the calendar branch; leave the
landing-page files on `dev`.

Restoring `test/run.js` brings the 126-test suite back immediately. That is the
single highest-value action in this document.

### 2. Recover Phases 1–3 before any calendar work resumes

The four missing modules and four missing test files exist in whatever tree
produced `a98c9d2` / `ce0a5bc` — neither commit is present in this repo, and no
`feature/calendar-integrations` branch exists locally. Until those arrive, the
calendar feature cannot be tested, mounted or deployed, and
`20261006_business_groups.sql` **must not be applied** — it would add two empty
tables to production for code that cannot run.

### 3. Ship Group A on its own

1. Fix the one `tsc` error (it travels with `Integrations.tsx`, so it leaves
   `dev` in step 1 anyway).
2. Push `dev` → Vercel **preview** URL. Look at the new `/` there.
3. `npm run build` + 35/35 green, then merge `dev` → `main` for the frontend
   only. **No server deploy, no migration** — Group A needs neither.

Production API stays on v35 / image `.30`, untouched.

### 4. Backend changes, when they come

The rule that keeps production safe is the one already holding: additive only.
New routes mounted in `api/index.js`, new tables created by new migrations,
nothing existing altered or dropped. A new table no deployed code reads is
inert; a new route no deployed image serves is absent. That is why Group A can
ship today while Group B waits — and why the pre-flight before any server
deploy still applies.

2. **Is the new `/` approved for production?** It replaces `Home` for every
